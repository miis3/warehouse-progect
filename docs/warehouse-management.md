# إدارة المستودع — النسخة المرشحة للاختبار

## الحالة والنطاق

العمل على `feature/warehouse-management` فقط. لم يتغير `main` أو نشر GitHub Pages الحالي.
الواجهة الأصلية في `warehouse-project/site/dist`، وتعمل دون عملية بناء أو إطار واجهات جديد.
خدمة الاختبار المعزولة هي مشروع Supabase `warehouse-management-staging`، مرجعه `gpiltdkbrryfhwqisioe`، ولا تتطلب خادمًا مدفوعًا مستقلًا.

## التشغيل للاختبار

من جذر نسخة الفرع:

```sh
npm ci --ignore-scripts
npm run check
npm test
python -m http.server 8000 --directory warehouse-project/site/dist
```

افتح `http://localhost:8000/`. الواجهة تتصل بقاعدة Supabase التجريبية الحقيقية؛ أي بيانات تدخلها يدويًا هنا تُحفظ فيها. الاختبارات الآلية تستخدم قاعدة مؤقتة منفصلة.
لا تفتح `index.html` مباشرة من القرص، ولا تستخدم منفذًا مختلفًا دون تحديث قائمة عناوين الاتصال المسموحة في الخدمة.

حساب المدير الأول أُنشئ باسم المستخدم `admin`. كلمة المرور تُسلّم في ملف خاص خارج GitHub. من دخول الإدارة يمكن تغيير كلمة المرور وإنشاء حسابات الأمناء بأسمائهم الفعلية؛ لم ننشئ أسماء وهمية للأمناء الثمانية.

## الوظائف

- دخول العامل بالاسم والرقم الوظيفي فقط؛ تطبيع الأرقام العربية والفارسية. تُستخدم بيانات الجلسة عند إرسال الطلب دون تكرار إدخالها.
- دخول المدير والأمين باسم مستخدم وكلمة مرور؛ التحقق من كلمة المرور عبر Supabase Auth.
- البحث في المعدات والملحقات الفعلية، مع الموقع والصندوق والكمية الأصلية والحالة. تبقى المعدات غير المتاحة ظاهرة.
- طلب استلام قطعة أو عدة قطع من المعدة، أو الصندوق كاملًا. لا تتكون عهدة قبل اعتماد الأمين.
- «عهدتي وسجلي» للعامل، وتسليم من عهدته فقط. لا يرى سجلات الآخرين.
- فحص مستقل عند الخروج وعند الإرجاع، مع اسم الأمين والتوقيت والملاحظات. التوقيت المعروض بتوقيت الرياض.
- إدارة الصيانة والتعطل والحالة؛ منع خروج المعدات غير الصالحة. حفظ كل تغيير في سجل ثابت.
- إضافة/تعديل المعدات والصناديق ومواقعها، ومراجعة الكميات وإضافة قطع دون حذف سجلاتها السابقة.
- باركود عام لكل صندوق بمعرّف ثابت `#box=UUID`، يستمر عند تعديل الاسم أو الموقع. العرض العام لا يكشف أسماء العاملين أو عُهدهم أو سجلاتهم.
- الخريطة والصور وفتح الصندوق وإغلاقه والروابط التجريبية السابقة باقية.

## البيانات المحفوظة وما يحتاج مراجعة ميدانية

192 موقع تخزين، 32 صندوقًا موزعًا في برافو، و258 بندًا مصدره الكشف (257 بندًا مسمى، بينها مجموعات وملحقاتها).
لم نحذف أو نعدّل كشوف Excel الأصلية أو صور المعدات أو ملفات بيانات المصدر.
أسماء الصناديق المتكررة محفوظة كصناديق مستقلة. ملف `docs/inventory-review.md` يشرح الفروق.

لا توجد قطع تشغيلية مفترضة. من «المعدات والصناديق» يختار الأمين الصندوق ثم «مراجعة الكمية والحالة» ويُدخل العدد الذي فحصه فعليًا. تحتفظ الواجهة بالكمية الأصلية في الكشف منفصلة عن العدد المعتمد. المجموعات لا تُحسب كمعدة مستقلة فوق ملحقاتها. الصندوق SA-025 وبند غير مسمى ينتظران استكمال المعلومات الأصلية.

## الصلاحيات وحماية السجل

- لا يوجد Local Storage أو Session Storage للحسابات أو العهد أو السجل. رمز الجلسة في ذاكرة الصفحة فقط؛ إعادة تحميل الصفحة تتطلب الدخول مجددًا. الخمول 15 دقيقة، والمدة القصوى 8 ساعات.
- دخول العامل بالاسم والرقم الوظيفي هو القرار المعتمد، وليس إثبات هوية قويًا؛ من يعرفهما يمكنه استخدام الحساب. الاعتماد النهائي لدى الأمين.
- تحقق JWT عند بوابة Edge Function مفعّل. المفتاح الموجود بالواجهة مفتاح `anon` عام؛ لا يثبت هوية العامل ولا يمنح صلاحية الإدارة. كل عملية خاصة تتحقق أيضًا من رمز جلسة عشوائي وصلاحية وملكية داخل قاعدة البيانات.
- مفتاح `service_role` موجود في بيئة Supabase للخدمة فقط. لا تُرسل كلمة مرور الإدارة أو رموز Supabase Auth إلى GitHub أو تخزين المتصفح.
- مخطط `warehouse` خاص، مع منع الوصول المباشر وسياسات RLS. دوال الوصول في `public` مسموحة لدور الخدمة فقط، وتتأكد من الجلسة والصلاحية قبل تنفيذ العملية.
- تغييرات السجل وحذفه وTRUNCATE مرفوضة بواسطة قاعدة البيانات؛ ملاحظات الخروج لا يمكن استبدالها عند الإرجاع. مالك قاعدة البيانات الذي يغيّر البنية ليس ضمن ضمان عدم التعديل من التطبيق.
- الطلبات قابلة لإعادة المحاولة بمفتاح ثابت، واعتماد القطع داخل معاملة مع أقفال وترتيب ثابت وقيد يمنع عهدتين نشطتين للقطعة نفسها.
- تعطيل حساب يمنع استمرار استخدامه، وتغيير كلمة المرور يبطل جلسات الإدارة الأخرى. إنشاء المدير الأول محمي برمز إعداد أحادي الاستخدام محفوظ كتجزئة.

## الاختبارات المنفذة وحدودها

- `npm run check`: صياغة JavaScript ومسارات ملفات الواجهة والأصول النسبية وإعداد JWT وعدم حفظ الجلسات في تخزين المتصفح.
- `npm test`: 16 اختبارًا ناجحًا؛ بيانات المصدر، صلاحيات الأدوار وملكية السجلات، اعتماد الاستلام والإرجاع، حماية السجل، تعارض الاعتمادات، الصندوق الكامل، الإدارة وكلمات المرور، وتفاعل الواجهة العربية من البحث وحتى الإرجاع والباركود.
- محرك اختبارات قاعدة البيانات PGlite هو PostgreSQL محلي مؤقت. اختبار إرسال اعتمادين يتحقق من عدم تكرار العهدة، لكنه ليس اختبار ضغط متعدد الاتصالات لخادم إنتاج.
- فحص خدمة Supabase المنشورة: الطلب دون مفتاح يُرفض؛ الكتالوج العام يعمل؛ العملية الخاصة دون جلسة تُرفض؛ دخول المدير وقائمة الحسابات يعملان؛ إعادة استخدام رمز الإعداد مرفوضة؛ الجلسة الموقوفة بعد الخروج مرفوضة.
- `tests/staging-transaction.sql` نُفذ على Supabase الفعلي: استلام واعتماد وإرجاع وحالة صيانة وسجل غير قابل للتعديل، ثم ROLLBACK. بقيت البيانات التشغيلية خالية من عمال/قطع/عهد الاختبار.
- فحص Supabase الأمني بعد تفعيل Auth يعرض تنبيهًا واحدًا: فحص كلمات المرور المسرّبة غير مفعّل. هذه الميزة متاحة لخطة Pro فما فوق؛ لم تتم ترقية الخطة أو إضافة تكلفة. لا توجد ملاحظات على صلاحيات الجداول. [شرح حماية كلمات المرور](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection). فحص الأداء يعرض INFO عن فهارس لم تُستخدم بعد في هذه القاعدة الجديدة؛ أُبقيت لدعم العلاقات والسجل: [تفسير الفهارس غير المستخدمة](https://supabase.com/docs/guides/database/database-linter?lint=0005_unused_index).
- اختبارات الواجهة عبر Happy DOM تختبر السلوك ولا تُعد فحصًا بصريًا نهائيًا لشاشة لمس أو هاتف. المتصفح السحابي منع فتح الخادم المحلي برسالة `net::ERR_BLOCKED_BY_CLIENT`؛ لذلك لم يُعتمد فحص بصري فعلي للنسخة في المتصفح.

## قبل الانتقال للموقع الحي

1. مراجعة الواجهة على شاشة المستودع والجوال، وخاصة فتح الصندوق وحجم الأزرار.
2. المدير يغيّر كلمة المرور الأولية ويُنشئ حسابات الأمناء بأسمائهم.
3. الأمناء يراجعون الكميات والحالات وفق الموجود فعليًا؛ البيانات غير المعتمدة تبقى ظاهرة ولا تُعار.
4. الدمج والنشر قرار منفصل؛ هذه المرحلة لم تغيّر الموقع الحي. بعد الدمج لاحقًا يبقى نشر Pages من `warehouse-project/site/dist` كما هو، ولا تُرفع الخدمة الخلفية من Workflow النشر الحالي.
